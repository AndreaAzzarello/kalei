# Ticket 0 — Feasibility spike

Ticket 0 proves, with measurements, the claims that the design cannot settle on paper. It writes **no product code**: spike code is throwaway, kept on a branch, and only the measured results and decisions return to the documents. Each test has a number to hit; below the "fail" line the stated fallback applies and the named ADR or requirement is changed. Nothing here is solved in words: a row stays open until it has a measured result recorded in `HISTORY.md` and the ADR it unblocks.

**Names**: "Ticket 0" in the other documents means this document and the spike tickets that carry out its proofs: 01–04 (Windows), 34 (global gesture), 35 (Linux) and 36 (macOS); the tickets themselves are numbered from 01 ([tickets](tickets/README.md)).

## Reference machines
- **Main (worst case, reproducible)**: Hyper-V virtual machine, Windows 10 22H2, 2 vCPU, 4 GB RAM, virtual SSD stored on a **SATA SSD** of the host (the host PC's other disk is NVMe). No HDD limit applies: a start-up measured here is a valid measure, not a slow-disk artefact. The thresholds for start-up, memory and Donut latency are measured here.
- **Windows 11**: the owner's desktop PC with two monitors; also used to try the Donut across screens and with different DPI.
- **macOS**: the owner's Mac mini (Apple M1, 8 GB RAM), for M1–M6.
- **Linux**: virtual machines with Ubuntu 24.04 and the current Fedora, for L1–L6.

Timings are the median of 10 runs, cold (after a reboot, or with the file cache dropped for the first run); the machine, Windows build and run count go in the report. Sizes are measured on the final published artifact.

### W7 — Cold-start breakdown on the reference VM (ticket 03c, issue [#56](https://github.com/AndreaAzzarello/kalei/issues/56), run 2026-11-11)
Machine: Hyper-V Windows 10 22H2 build 19045.6456, 2 vCPU, 4 GB, SATA SSD host disk, Defender real-time protection on (the VM's checkpoint "aggiornato"). Code and kit: branch `spike/03a-build` (commits `92efe87` and `8abb070`, throwaway, not merged). Same window, same measure as #47 (process creation to the second animation frame after the window opened), plus phase markers.
- **Method**: six variants, all self-contained ReadyToRun + trimming; reboot before each start, 150 s settle time (uptime at every start 150–151 s), one start, reboot. One unmeasured warm-up start of each variant before the first reboot (it makes Defender scan the new files). Rounds 1–5 ran all six variants, rounds 6–10 only a, b, d (reduced plan to save time: c, e, f have **5** starts instead of 10), 45 valid starts, 0 failed, 0 interrupted. The order rotated every round; variants are compared **in the same round** because the baseline drifts upwards.
- **Variants**: **a** baseline of #47 with the markers; **b** window shown at once with minimal content, full view after the second frame; **c** `Avalonia.Desktop` replaced by `Win32` + `Skia` + `HarfBuzz`, explicit default font, ComboBox filled after the second frame (this removes one assembly, `Avalonia.Desktop.dll`; the baseline never loaded X11, FreeDesktop or Native); **d** ReadyToRun composite, `TieredPGO` off, non-concurrent GC, `UseSystemResourceKeys`; **e** software rendering (`Win32RenderingMode.Software`, no ANGLE/EGL); **f** b + c + d.

| Variant | Starts | Second frame, median (min–max) | Paired difference to a, same round | ≤ 1000 ms | Complete content, median (max) |
|---|---|---|---|---|---|
| a baseline | 10 | **968** (925–993) | – | 10/10 | 968 (993) |
| b window first | 10 | 918 (887–945) | −49 | 10/10 | 986 (1014; 2 of 10 above 1000) |
| c lean start | 5 | 961 (950–974) | +23 | 5/5 | 977 |
| d runtime options | 10 | 1528 (1509–2193) | +578 | 0/10 | 1528 |
| e software rendering | 5 | **811** (776–827) | −150 | 5/5 | 811 |
| f b + c + d | 5 | 1493 (1467–1535) | +530 | 0/5 | 1523 |

- **Where the time goes (baseline a, median from process creation, ms)**: first managed code 210 (apphost, host and CLR start; cannot be split without event tracing), Main 278, AppBuilder 372, Avalonia and Skia platform services 655 (this step alone takes 280), theme loaded 736, window created 810, first layout 883, window opened 892, second frame **968**. By share: up to Main 29%, builder + platform 39%, theme + window + layout + second frame about 31%. CPU time (user + kernel) is about 313 ms of 968: about two thirds of the start is waiting; whether it is disk, Defender scanning image loads or something else was not measured.
- **Reading**: **b** moves the second frame earlier by 49 ms but the complete window arrives 18 ms *later* than in a: no real gain, and the cost is before the window exists. **c** gives nothing (+23 over 5 rounds). **d** is much worse in every phase (first managed code 292 against 210, platform services 427 against 280) with less CPU (211 ms against 313): the 17 MB composite image makes the cold start wait more; the Microsoft pages read (ReadyToRun, compilation and garbage collector settings, trimming options) state no start-up gain for composite, TieredPGO, concurrent GC or system resource keys. **f** inherits d's loss. **e** is the only lever that worked: platform services fall from 280 to 153 ms (−127), the second frame by about 150 ms.
- **Against #47**: the baseline passes here (median 968, max 993) where #47 failed (median 1122.7, min 1020.8, max 1614.8, the first start the slowest). The method differs (warm-up start, rotated order, markers, state of the VM) and the data cannot say which factor weighs. Within this series the baseline rises from 925 ms (round 1) to 993 ms (round 10), about 7 ms per round, cause not measured.
- **Not verified**: Native AOT; software rendering on a PC with a GPU (Donut latency, animation, CPU; ticket [03d](tickets/03d-software-rendering-vs-gpu.md)); whether ANGLE on the VM already ran on a software Direct3D adapter; the cause of the drift and of the gap to #47; a lighter theme than Fluent (about 230 ms are spent in theme, window creation and layout; not tried); the embedded font Bricolage Grotesque, which is not in the spike and may add time in the real window (ticket 10a). The "ReadFile" counter in the raw data counts only read calls, not mapped images, so it says nothing about disk. c, e and f have 5 starts, so their medians are indicative.
- **Owner decision (2026-11-12)**: the W7 threshold is revised to **1.3 s** and the UI ships with ReadyToRun + trimming; see the next section.

### W7 — Decision after ticket 03c (2026-11-12)
- **Threshold revised**: cold start of the UI on the main reference machine (2 vCPU, 4 GB, SATA SSD, Defender), **median of 10 cold starts at the second frame ≤ 1.3 s** (was 1 s).
- **Why**: the cold start is the worst case (first start after a reboot on the weakest machine). The value measured for ReadyToRun + trimming goes from about 970 ms (files already scanned by Defender, ticket 03c) to about 1120 ms (first start after the copy or install, #47), and both stay under 1.3 s with a headroom of 332 ms and 177 ms. The 1 s limit was an initial value that was not derived from data. It was revised after the measures, on 2026-11-12, with the figures above.
- **Warm target**: none existed in the documents; the 418 ms of the Windows 11 PC (ticket 03a) is a measurement, not a target, and it stays recorded as such.
- **Consequences**: the UI is published with ReadyToRun + trimming; Native AOT is no longer mandatory and stays an opportunistic trial after the CI of ticket [39](tickets/39-ci-github-actions.md) (ticket [38](tickets/38-native-aot-trial.md)), with the numbers to beat on the VM (baseline 968 ms, software rendering 811 ms, same kit, no automatic sign-in needed). Software rendering is **not** adopted; ticket [03d](tickets/03d-software-rendering-vs-gpu.md) compares it with the GPU on the Windows 11 PC. Open risk: the Bricolage Grotesque font is not in the spike and may raise the time in the real window; it is measured again when the real window exists (ticket [10a](tickets/10a-main-window-file-card.md)).

### W1, W2, W3, W4, W7, W8 and W10 — Reference VM (issue #47, run 2026-11-11)
Machine: **Hyper-V VM, Windows 10 Pro 22H2 build 19045.6456, 2 vCPU, 4 GB** (host disk: SATA SSD). Screen 958×925 at 100% (96 DPI), one screen. Windows Firewall service and BFE running, the three profiles on, no third-party firewall, Microsoft Defender the only antivirus, no .NET SDK. The report records the token as not elevated and not a member of Administrators. Internet reachable (controls of W2). Package: the spikes of tickets 01, 03a and 04 published self-contained and run by one script outside the repository; the sanitised report was composed on the host from the raw state files (no user name, computer name or personal path; checked by search). .NET 10.0.13, libvips 8.18.7.
- **W1, W2, W3, W4 pass on Windows 10 22H2** (15 pass, 0 fail, 0 inconclusive, exit 0): AVIF 4,202 bytes and WebP 9,780 bytes from inherited handles in AppContainer + Job Object, checked in pixels; TCP, UDP, DNS and loopback fail inside and succeed outside; TIFF 887 seeks and AVIF 226 through seekable handles; the Worker loads after the `icacls` grant with no administrator rights; filesystem by path denied (0 of 6), memory cap 2 GB, timeout, no child process, kill-on-close (7 ms and 0 ms). Details and the AVIF size difference with Windows 11: [ADR 0003](adr/0003-worker-sandbox-and-handle-passing.md#result-on-the-reference-vm-issue-47-w1w4-2026-11-11). ADR 0003 and 0006 are now accepted for both systems; the stopped-firewall states stay open (W19, W20).
- **W8 pass on Windows 10 22H2**: the trimmed Worker starts and its 10 smoke tests pass (10 of 10, "ALL PASS"). The size estimate is machine independent (42.7 MB, above).
- **W7 FAIL for ReadyToRun + trimming against the original 1 s threshold (revised to 1.3 s on 2026-11-12: the median of 1122.7 ms below passes it; see the two W7 sections above)**: the window of the spike `AotWindow`, 10 cold starts (reboot before each, 150 s for the desktop to settle, then one start; the same window and the same measure, process creation to the second animation frame, as on the Windows 11 PC): 1614.8, 1234.8, 1054.6, 1394.1, 1140.1, 1036.9, 1111.8, 1066.5, 1133.6 and 1020.8 ms. **Median 1122.7 ms** against the 1000 ms threshold (min 1020.8, max 1614.8): all ten starts are above it, the first the slowest. The 418 ms of the Windows 11 PC is warm on 16 CPUs and not comparable. Native AOT is not measured (ticket [38](tickets/38-native-aot-trial.md)); **ADR 0001 unchanged, the decision is open**: ticket [03c](tickets/03c-w7-cold-start-breakdown.md) (issue [#56](https://github.com/AndreaAzzarello/kalei/issues/56)) first breaks the start down into phases and tries optimisations without AOT, then the owner chooses between AOT, a revised threshold and optimisation.
- **W10 pass, criterion 1 of ticket 04**: 10 valid cold rows (first drag-enter of each new process; one screen at 100%, render scaling 1.00): frame2 **median 32.2 ms, max 53.5 ms**; frame1 median 19.3 ms, max 28.4 ms; **10 of 10 under 100 ms**; ring inside the window 10 of 10; drops Copy with the source unchanged 10 of 10; the Format is known before the drop (hint from the extension, header sniff `png`; one `.jpg` that is a PNG was recognised). Limits of this series: every drop was **one file** (the `files` column is 1 in all rows, the kit asked for the 5 samples), so the file-list cost is the one-file case; one screen, so nothing about scaling (that is the Windows 11 result); whether the VM was rebooted before this series is not recorded, each run is a new process on a warm file cache like the Windows 11 series. The owner saw a median of 31.4 ms in a first round at the screen; that round's log was deleted when the script restarted the phase (kit bug below), so the 10 rows are from the second round and 31.4 ms is not in the data.
- **Temporary automatic sign-in (a W7 aid, removed)**: the system task reported `ok`, "LSA secret removed" and "Winlogon values restored and verified" (15:52 UTC, not forced). The report's own check of the Winlogon registry values did not run, because the VM had already been returned to its checkpoint, which removes everything anyway.

The end of the crash (probably out of memory) and the original error text were not seen. Fix: cast the lines to `[string]`. The firewall kit of W19 does not use that code.
- **Not verified**: W19 and W20 (stopped-service and allow-rule states, canary); third-party firewall or antivirus other than Defender; HEIC through WIC; Native AOT; Donut with the 5 sample files and with scaling on the VM; the Winlogon registry check after the sign-in cleanup.

### W10 — In-app Donut spike (ticket 04, run 2026-11-10)
Machine: **Windows 11 dev PC — to repeat on the reference VM (Hyper-V Win10 22H2, 2 vCPU, 4 GB), issue [#47](https://github.com/AndreaAzzarello/kalei/issues/47)**. Three monitors: index 0 1920×1080 at 100% (primary), index 1 3840×2160 at 300% (its right edge touches the left edge of index 0), index 2 1920×1080 at 100% (right of index 0). Avalonia 12.1.6, .NET 10. Code, 32 tests of the pure logic (pass) and scripts: branch `spike/04-donut` (not merged). Logs hold only extensions, Formats, sizes and timings.
- **Latency (first drag-enter of each new process; warm file cache, not a rebooted machine; frame2 = second frame tick after the first drag-enter handler call, the figure compared with 100 ms)**:

  | Series | Valid cold rows | frame2 median | frame2 max | frame1 median | ≤ 100 ms |
  |---|---|---|---|---|---|
  | monitor 0, 100% | 6 | 26.0 ms | 27.9 ms | 17.3 ms | 6/6 |
  | monitor 1, 300% (window also over monitor 0) | 4 | 24.5 ms | 26.1 ms | 16.5 ms | 4/4 |
  | window across the edge between monitors 0 and 2, both 100% | 5 | 30.2 ms | 31.4 ms | 20.6 ms | 5/5 |
- **Missing rows explained (not "the first run is not logged")**: the first version wrote each row from a 1 s timer after the drag-enter, and with `--exit-after-drop` the window closed about 0.5 s after the drop, so a drop within roughly 0.5 s of the drag-enter exited before the row was written. Of the 10 + 5 + 12 processes, 15 left a row. Re-entries of the same process (7 rows, frame2 3–10 ms, warm) had been counted in the first summaries and lowered the medians; the table above excludes them. Fixed on the spike branch (row written at the second frame, column `enter`, `run-cold.ps1` repeats a run without a valid row, `-Exe` for a published build). The series above come from the first version; **no series has the 10 valid cold runs the criterion asks for**.
- **Format known before the drop (pass)**: at drag-enter the window already gets the file list and names (`TryGetFiles`, about 7 ms), so the extension hint is ready in about 11 ms and a header sniff of 16 bytes (about 1–2 ms, after the overlay is up) already identifies the Format (it recognised a `.jpg` that is a PNG). An unknown extension shows the hub as "analysing". Nothing needs to wait for the drop.
- **Drop is Copy and the source is untouched (pass)**: 27 of 27 drops in the three series report `Copy` and leave the first file unchanged (SHA-256 before and 500 ms after, size, last-write time).
- **Scaling proof (second run, log v2, 2026-11-10; monitor 0 set to 150%, then 200%; monitor 2 at 100%)**:

  | Series | Valid cold rows | frame2 median | frame2 max | frame1 median | ≤ 100 ms | Ring inside window |
  |---|---|---|---|---|---|---|
  | monitor 0, 150% | 10 of 10 processes | 36.0 ms | 43.5 ms | 25.1 ms | 10/10 | 10/10 |
  | 150% / 100%, window across the edge of monitors 0 and 2 | 5 (7 re-entries excluded) | 28.0 ms | 38.8 ms | 19.3 ms | 5/5 | 5/5 |
  | monitor 0, 200% | 5 | 28.2 ms | 33.0 ms | 18.7 ms | 5/5 | 5/5 |
  | 200% / 100%, window across the edge of monitors 0 and 2 | 5 of 5 attempts | 26.3 ms | 27.2 ms | 18.2 ms | 5/5 | 5/5 |

  Drops: 25 of 25 `Copy`, source unchanged 25 of 25. Seen by eye in every round, at 150% and 200%, also with the cursor on the 100% half and on the edge between the monitors: ring whole and centred on the cursor. The 150% series has the highest median (36.0 ms, max 43.5 ms), well under 100 ms; no cause measured.
- **Why the recorded screen differs (0 at 150%, 2 at 200%)**: `screenIdx` and `screenScaling` come from `Screens.ScreenFromVisual`, called when the row is written; the Avalonia documentation says only that it returns the screen containing the visual. The straddle mode centres the window on the edge between two screens, so both halves are nearly equal in size (at 200%: 1800 px wide, about 900 px on each side) and which screen is "the one containing it" can fall either way; the rule Windows uses to pick it (largest intersection) is our reading, not checked. ### Network isolation and the firewall (primary sources, read 2026-11-10; plan for W19 and W20)
- **What Microsoft documents**: AppContainer isolation is done by WFP filters: the "Windows Application Isolation" sublayer ("These filters apply to applications running in an App-Container and requires App-Container network capabilities"), "UWP default" and "AppContainer loopback" block filters, and the Base Filtering Engine adds and removes the filters. Sources and quotes: [ADR 0003](adr/0003-worker-sandbox-and-handle-passing.md#what-enforces-the-network-block-microsoft-documentation-read-2026-11-10).
- **What Microsoft does not document** (none of the four pages read says it): the behaviour of AppContainer network access with the Windows Firewall service or the BFE stopped, the profiles off, or a rule or policy that allows the traffic (fail-closed or fail-open). **Not verified**: our test on Windows 11 ran with the BFE and the firewall service running and all profiles on.
