## What to build
At start-up Kalei proves, on this PC, that a sandboxed Worker cannot reach the network, without any outbound connection to the Internet (two local TCP attempts, one to the Core and one to a non-routed documentation address), and shows the "no network" promise only when it has. The block is enforced by Windows Filtering Platform filters that depend on Windows services, and Microsoft does not document what happens when they are off, so the promise is checked, not assumed (see the Network canary section of architecture.md).

## Acceptance criteria
1. A canary mode of the built-in Worker runs in the same sandbox profile as every Worker, with no file handles, and tries two TCP connects in parallel: **local** to a listener the Core opens on 127.0.0.1 (random port) and **net** to 192.0.2.1:443 (TEST-NET-1, RFC 5737, a documentation address that is not routed on the Internet). The destinations are fixed in code, not configurable. There is no probe to a real host and no DNS probe (a name lookup is done by the DNS Client service, not by the filter on the Worker, and would need a real host name); no outbound connection to the Internet exists in the design, and a test (static check plus a fake launcher) asserts that no other destination is used. Before the Worker starts the Core connects to its own listener as a positive control; if that fails the verdict is `unproven`.
2. The verdict follows the Winsock code of the `net` probe: immediate `WSAEACCES` (10013) is blocked; a connection made is `leaked`; `WSAETIMEDOUT`, `WSAENETUNREACH`, `WSAEHOSTUNREACH`, `WSAECONNREFUSED` and any other code are `unproven` and the code is logged. `isolated` only if the Worker started and replied, `local` was blocked (refused or timed out) and `net` gave `WSAEACCES`; `leaked` if either connected; `unproven` in every other case; `pending` before the first result. A test with a fake launcher covers each row, including a probe that "connects" and a Worker that crashes.
3. Timing: timeouts are 200 ms (local) and 1,000 ms (net), run in parallel; the verdict arrives within 1.2 s in the worst case and within 10 ms from the cache; the canary never runs on the UI thread and a Conversion never waits for it. Measured on the Hyper-V VM and on the Windows 11 PC.
4. It runs in the background at every app start (and at the first run after install), and before a Batch starts if the cached verdict is older than 10 minutes or the service state changed. The cache (verdict, time, OS build, service states) is kept in memory and in the data folder, is never reused after an OS build change or a service state change, and there is no timer.
5. The Core reads the state of the Base Filtering Engine and of the Windows Firewall service through the Platform adapter, without administrator rights, in at most 5 ms; it is logged as an additional signal, the verdict is decided by the probes.
6. Only `isolated` shows the promise ("Converters have no network access on this PC, checked at start-up"). Any other verdict hides the promise everywhere in the app and shows, at most once per session, the neutral notice `NETWORK_ISOLATION_UNPROVEN`: IT "Isolamento di rete non verificabile su questo PC al momento. Le conversioni funzionano normalmente." / EN "Network isolation can't be verified on this PC right now. Conversions work normally." No alarm styling, no blocking dialog, no action required; Settings shows the detail. Conversions are not blocked. The README and PRD wording says the promise is checked at each start-up.
7. Log event `NET_CANARY` with: verdict, the Winsock code of each probe, the states of the two services (running, stopped, unknown), duration in ms and OS build; no address, host name, path or user name. The S10 log scan passes with the event present.
8. The notice and the log event code are added to the message catalogue and the ipc-spec (messages `Canary` and `CanaryResult`); the catalogue test finds no code without a message.
9. W20: on the Hyper-V VM, with a healthy and with a broken sandbox (outbound allow rule for the AppContainer profile), in each state of W19 and also online, offline, and with the network adapter disabled, the code of each probe is recorded and the verdict is `isolated` only where `net` gave `WSAEACCES` and `local` was blocked; zero false `isolated`. If a healthy sandbox gives `WSAENETUNREACH` offline, the verdict there is `unproven` and the promise stays hidden; the owner decides with the numbers whether that is acceptable. Results go in ticket-0 Results; a single false `isolated` keeps the ticket open.
